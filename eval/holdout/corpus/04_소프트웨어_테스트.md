# 소프트웨어 테스트

## 테스트의 기본 원리
완벽한 테스트는 불가능하다. 테스트는 결함이 있음을 보여줄 수는 있지만 결함이 없음을 증명할 수는 없다.
결함 집중(파레토 법칙): 결함의 대부분은 소수의 모듈에 집중되어 있다. 전체 결함의 80%가 20%의 모듈에서 발견된다고 본다.
살충제 패러독스: 같은 테스트 케이스를 반복하면 더 이상 새로운 결함을 찾지 못하므로, 테스트 케이스를 주기적으로 검토하고 개선해야 한다.
오류-부재의 궤변: 결함을 모두 없애도 사용자의 요구사항을 만족하지 못하면 그 소프트웨어는 품질이 높다고 할 수 없다.

## 검증과 확인
검증(Verification)은 소프트웨어가 명세서대로 올바르게 만들어졌는지, 즉 제품을 올바르게 만들고 있는지 확인하는 것이다.
확인(Validation)은 만들어진 소프트웨어가 사용자의 요구를 충족하는지, 즉 올바른 제품을 만들었는지 확인하는 것이다.

## 화이트박스 테스트
화이트박스 테스트는 모듈의 내부 소스 코드와 논리 흐름을 보면서 모든 경로를 검사하는 테스트로, 구조 기반 테스트라고도 한다.
기초 경로 검사는 맥케이브가 제안한 기법으로, 순환 복잡도를 이용해 독립적인 실행 경로의 수를 구하고 그 경로들을 모두 테스트한다. 순환 복잡도는 간선 수 - 노드 수 + 2 로 계산한다.
문장 커버리지는 모든 문장을 최소 한 번 실행하는 것, 분기(결정) 커버리지는 모든 조건문의 참과 거짓을 최소 한 번씩 실행하는 것, 조건 커버리지는 조건식 안의 각 개별 조건이 참과 거짓을 한 번씩 갖도록 하는 것이다.

## 블랙박스 테스트
블랙박스 테스트는 내부 구조를 보지 않고 요구사항 명세에 따라 입력과 출력만으로 기능을 검사하는 테스트로, 명세 기반 테스트라고도 한다.
동등 분할(동치 분할)은 입력 자료를 같은 결과가 나오는 그룹으로 나누고 각 그룹의 대표값으로 테스트한다. 예를 들어 점수가 0~59면 불합격, 60~100이면 합격일 때 각 구간에서 하나씩 고른다.
경계값 분석은 입력 조건의 경계에서 오류가 많이 생긴다는 점을 이용해 경계값과 그 바로 앞뒤 값으로 테스트한다. 앞의 예에서는 59, 60, 100, 101 같은 값을 쓴다.
원인-결과 그래프는 입력 조건(원인)과 출력(결과)의 관계를 그래프로 분석해 테스트 케이스를 만든다.
오류 예측은 테스터의 경험과 감으로 오류가 날 만한 곳을 찾아 테스트한다.

## 테스트 단계
단위 테스트는 하나의 모듈이나 함수처럼 가장 작은 단위를 독립적으로 검사한다.
통합 테스트는 단위 테스트를 마친 모듈들을 결합하며 인터페이스와 상호작용의 결함을 찾는다.
시스템 테스트는 통합된 전체 시스템이 기능 요구사항과 비기능 요구사항을 만족하는지 검사한다.
인수 테스트는 사용자가 요구사항을 충족하는지 확인하고 시스템을 받아들일지 결정하는 테스트다. 알파 테스트는 개발자 환경에서 사용자가 개발자와 함께 수행하고, 베타 테스트는 실제 사용자 환경에서 개발자 없이 수행한다.

## 통합 테스트 방식
하향식 통합은 상위 모듈부터 하위 모듈 방향으로 통합하며, 아직 만들어지지 않은 하위 모듈 대신 스텁(Stub)을 쓴다.
상향식 통합은 하위 모듈부터 상위 모듈 방향으로 통합하며, 상위 모듈 대신 하위 모듈을 호출해 주는 테스트 드라이버(Driver)를 쓴다. 하위 모듈들을 묶은 클러스터 단위로 진행한다.
빅뱅 통합은 모든 모듈을 한꺼번에 결합해 테스트하는 방식으로, 결함이 생겼을 때 원인을 찾기 어렵다.

## 테스트 오라클
테스트 오라클은 테스트 결과가 맞는지 판단하기 위한 기준이다. 참 오라클은 모든 입력에 대해 기대 결과를 제공하고, 샘플링 오라클은 특정 입력에 대해서만, 추정(휴리스틱) 오라클은 특정 입력에 대해 기대 결과를 주고 나머지는 추정으로 판단한다. 일관성 검사 오라클은 변경 전후의 결과가 같은지 확인한다.

## 회귀 테스트
회귀 테스트는 코드를 수정한 뒤 수정한 부분 때문에 기존에 잘 동작하던 기능에 새로운 결함이 생기지 않았는지 다시 확인하는 테스트다.
